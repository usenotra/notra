Every site comes with built-in analytics, and this page covers how to send visits to your own analytics tool as well, run your own JavaScript and control which origins your pages may load code from.

## Built-in analytics

Every site counts its own visitors and their time on page with nothing to install, and you can turn this off under **Settings → Danger zone**. Open the site's **Analytics** page for people and AI agents on the site, or **Traffic** in GEO for AI crawlers and referrals across all your domains. Neither page counts visits to previews. See [AI agents and search](/sites/agents#ai-traffic-analytics).

## Analytics integrations

Add a provider under `integrations` in `blog.json`, commit the file and deploy your site. Notra loads the provider on every live page and adds the hosts it needs to the [Content-Security-Policy](#content-security-policy). You can enable several providers at once.

The site's **Integrations** page edits the same configuration. Enter your provider's ID and review the JSON example. Valid changes save automatically as a draft of `blog.json`. The dialog shows whether changes are waiting, saving or saved. Closing it finishes any pending save; failed saves stay open so you can retry. Open **Review and publish** to publish your saved changes through your site's usual GitHub workflow, either as a pull request or a direct commit when allowed. The new settings take effect after the production deployment succeeds. Removing a provider also updates the draft and requires publishing.

<Note>
  Analytics integrations are disabled on preview deployments and during local development. Custom scripts still run there. If you install analytics through a custom script, you control when it sends events.
</Note>

### Google Analytics 4

In Google Analytics, open **Admin → Data streams**, create or select a web stream for your live site's URL, and copy its **Measurement ID**. It starts with `G-`.

```json blog.json
{
  "name": "Acme",
  "integrations": {
    "ga4": {
      "measurementId": "G-ABC123XYZ9"
    }
  }
}
```

Publish the configuration, visit your live site and check Google Analytics Realtime. Standard reports can take time to update.

### PostHog

Copy the public project API key from your PostHog project settings. It starts with `phc_`.

```json blog.json
{
  "name": "Acme",
  "integrations": {
    "posthog": {
      "apiKey": "phc_abcdefghijklmnopqrstuvwxyz0123",
      "apiHost": "https://eu.i.posthog.com",
      "sessionRecording": false
    }
  }
}
```

`apiHost` is optional and defaults to `https://us.i.posthog.com`. Set it to `https://eu.i.posthog.com` for EU Cloud, or to your self-hosted instance or HTTPS reverse proxy. Events go directly to this endpoint.

Session recording is enabled by default. Set `sessionRecording` to `false` to disable recording while keeping analytics enabled. Your PostHog project must also allow recording for your site's domain.

### Plausible

Use the domain you added to Plausible, without `https://`.

```json blog.json
{
  "name": "Acme",
  "integrations": {
    "plausible": {
      "domain": "blog.acme.com"
    }
  }
}
```

For self-hosted Plausible, add `"server": "plausible.acme.com"`. Use the server's hostname without a protocol or path, and include its port when needed (for example, `plausible.acme.com:8443`). Notra loads its script and sends events to that server. When omitted, the server is `plausible.io`.

### Databuddy

Copy the Client ID from your Databuddy dashboard.

```json blog.json
{
  "name": "Acme",
  "integrations": {
    "databuddy": {
      "clientId": "3ed1fce1-5a56-4db3-8df5-a1036322c999"
    }
  }
}
```

Notra validates provider settings in the dashboard, when saving and during builds. Invalid IDs, unexpected keys and invalid hostnames stop the change with an error. Remove a provider's object to disable it, then publish and deploy the configuration.

## Custom scripts

Every `.js` file outside the content folders runs on every page, whether it's `script.js`, a file in a `scripts/` folder or a file like `analytics.js` at the root. These files work like [custom CSS](/sites/customize/design#your-own-css) for JavaScript, while a `.js` file in `snippets/`, `blog/` or `changelog/` is a component you import instead.

```text
script.js               # runs first
analytics.js            # then every other script, sorted by path
scripts/chat-widget.js
scripts/tracking/hotjar.js
```

Notra loads every script on every page with `defer` from your site's own address, and the scripts run in the order shown above once the HTML has been parsed.

- These files are plain browser JavaScript rather than modules, so `import` and `export` don't work in them. To load a library from another host, use `document.createElement("script")`.
- The build checks the syntax without running your scripts, and a syntax error fails the build and shows the file and line.
- Your MDX can't import these files, so for a component, use a [snippet](/sites/custom-components) in `snippets/` instead.

```js scripts/external-links.js
// Open links to other sites in a new tab.
for (const link of document.querySelectorAll("main a[href^='http']")) {
  if (link.host !== location.host) {
    link.target = "_blank";
    link.rel = "noopener";
  }
}
```

## Content-Security-Policy

Every page comes with a `Content-Security-Policy` header that says where scripts may come from and which servers they may connect to, and Notra builds it from your repository.

- **Scripts** can come from your site, the analytics integrations you turned on and your `allowedOrigins`. Notra allows inline scripts only if they were on the page at build time and hashes each of them, so a script injected later doesn't run.
- **Connections** from `fetch`, beacons and WebSockets may go to your site, your integrations and your `allowedOrigins`.
- The policy doesn't limit **images, styles, fonts, videos and embeds**, so posts can still show images and videos from anywhere.

If your custom scripts or components load code from another host or call an API, add that origin:

```json blog.json
{
  "security": {
    "allowedOrigins": [
      "https://cdn.example-widget.com",
      "https://*.example-widget.com",
      "wss://*.example-widget.com"
    ]
  }
}
```

Origins must start with `https://` or `wss://` and have no path, and `https://*.example.com` covers every subdomain. A `wss://` origin only allows connections rather than scripts, and you can list up to 32 origins.

To turn the policy off entirely:

```json blog.json
{
  "security": { "contentSecurityPolicy": false }
}
```

If a script doesn't run, open your browser's developer console, which lists any request the policy blocked with the origin you need to add.
