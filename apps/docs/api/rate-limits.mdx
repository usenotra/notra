The Notra API rate limits the endpoints that start model runs, scans or other expensive work. Plain reads (listing posts, visibility data, feedback, schedules and so on) and deletes are not rate limited.

Each limited endpoint has its own bucket with a sliding window. Hitting the post-generation limit does not affect post updates or GEO scans. When a request would exceed a limit, the API returns `429 Too Many Requests` and does not run the request.

## Limits

Each limit is keyed in one of three ways:

- **Per key.** The bucket belongs to the API key making the request. Two keys in the same organization have separate budgets.
- **Per organization.** Every key in the organization shares one bucket.
- **Per IP.** The bucket belongs to the caller's source address.

### Content

| Endpoint | Limit | Keyed |
| --- | --- | --- |
| `POST /v1/posts/generate` | 10 requests / minute | per key |
| `PATCH /v1/posts/{postId}` | 60 requests / minute | per key |
| `POST /v1/brand-identities/generate` | 5 requests / minute | per key |
| `POST /v1/integrations/github` | 20 requests / minute | per key |

### Chats and agent

| Endpoint | Limit | Keyed |
| --- | --- | --- |
| `POST /v1/chats`, `POST /v1/chats/{chatId}` | 30 requests / minute | per organization |
| `POST /v2/eve/v1/session`, `POST /v2/eve/v1/session/{sessionId}` | 30 requests / minute (shared with chats) | per organization |

### GEO

| Endpoint | Limit | Keyed |
| --- | --- | --- |
| `POST /v1/projects/{projectId}/geo/scans` | 4 requests / hour | per organization |
| `POST /v1/projects/{projectId}/geo/sequences/{sequenceId}/run` | 10 requests / 10 minutes | per organization |
| `POST /v1/projects/{projectId}/geo/prompts/import` | 10 requests / 10 minutes | per organization |
| `POST /v1/projects/{projectId}/geo/competitors/import` | 10 requests / 10 minutes | per organization |
| `GET /v1/projects/{projectId}/geo/competitors/suggestions` | 10 requests / 10 minutes | per organization |
| `POST /v1/projects/{projectId}/geo/briefs` | 10 requests / 10 minutes | per organization |
| `POST /v1/projects/{projectId}/geo/briefs/{briefId}/approve` | 20 requests / 10 minutes | per organization |
| `POST /v1/projects/{projectId}/geo/agent-readiness/scan` | 10 requests / hour | per organization |

GEO limits apply across all projects in the organization. Four scans per hour is the total across every project, not four per project.

### Feedback

| Endpoint | Limit | Keyed |
| --- | --- | --- |
| `POST /v1/feedback/{organizationSlug}` | 30 requests / 10 minutes, plus 200 requests / hour | per IP, plus per organization |
| `POST /v1/feedback` | 120 requests / minute | per key |

<Note>
  Agents call `POST /v1/feedback/{organizationSlug}` without credentials. It is the only such endpoint, so Notra limits it per source IP address and per organization. Both limits apply at the same time. See [Agent Feedback](/feedback/send-feedback).
</Note>

## Response headers

Every response from a rate-limited endpoint, successful or not, includes both the IETF draft header names and the legacy `X-` names:

| Header | Meaning |
| --- | --- |
| `RateLimit-Limit` / `X-RateLimit-Limit` | Maximum requests allowed in the window |
| `RateLimit-Remaining` / `X-RateLimit-Remaining` | Requests remaining in the current window |
| `RateLimit-Reset` | Seconds until the window resets |
| `X-RateLimit-Reset` | Unix timestamp (seconds) when the window resets |
| `Retry-After` | Seconds to wait before retrying (only sent on `429`) |

Endpoints that are not rate limited do not send these headers.

## 429 response

When a request is rejected, the API returns:

```json
{
  "error": "Rate limit exceeded",
  "limit": 10,
  "remaining": 0,
  "reset": 1756800000000
}
```

`reset` is a Unix timestamp in milliseconds. The `Retry-After` header gives the same moment as a number of seconds to wait and is the simplest field to act on.

<Note>
  A `429` with `error: "API key rate limit exceeded"` and a `code` field comes from the authentication layer rather than an endpoint bucket. It means the key itself is throttled. See [Authentication](/api/authentication#error-responses).
</Note>

## Best practices

- Read `RateLimit-Remaining` and slow down before you hit zero.
- On `429`, wait for `Retry-After` seconds before retrying. Do not retry immediately.
- Use exponential backoff with jitter for `5xx` responses. Treat `429` as a hard wait, not a retry signal.
- GEO scans are the most expensive thing a key can trigger. Poll `GET /v1/projects/{projectId}/geo/scans/{scanId}` for the result instead of re-triggering.
- For bulk work (for example backfilling many posts), space requests evenly across the window instead of sending them in bursts.
