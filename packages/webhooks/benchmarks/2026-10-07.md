# Webhook worker benchmark — 2026-10-07

The retained changes reduce recovery work, not delivery guarantees. A scheduled
pass dispatching 500 events went from a P50 of **9,398 ms to 570 ms**; measured
Cloudflare CPU P50 went from **365 ms to 8 ms**. Idle passes and the delivery hot
path remain substantially unchanged. These are isolated development measurements,
not measurements of production or a promise about production percentiles.

A subsequent code-quality review consolidated the two queue batching adapters
and removed unused single-message service methods. Those cleanup changes were
validated locally; the remote benchmarks were not repeated. The measurements
below refer to the source snapshots in the original results bundle.

## Environment and method

- Baseline: repository commit `65a66b453`, with an unchanged copy of the webhook
  package source taken before editing. Measured final source is the `final/src/`
  snapshot in the original results bundle.
- One temporary Cloudflare Worker, two dedicated queues, and a separate Railway
  project/environment named `benchmark`. Neither the existing development
  database nor production resources were used for writes or deployments.
- A new, empty Neon project: PostgreSQL 18, AWS `eu-central-1`, fixed 0.25 CU.
  It used the lifecycle SQL fixture plus migrations `0105` and `0109`, with only
  synthetic organizations, endpoints, events, posts and GEO scans.
- Railway receiver in Europe, one Node 24 Alpine container. The receiver verified
  HMAC independently with Node crypto, recorded bounded in-memory receipt counts,
  and supported controlled response codes and delays. It did not log secrets.
- Same queue configuration throughout: batch size 10, timeout 1 second, maximum
  consumer concurrency 25. Final per-invocation concurrency remains **5**.
- Worker compatibility date `2026-09-01`, `nodejs_compat` and
  `global_fetch_strictly_public`; deployment CLI Wrangler 4.112.0, local Bun 1.4.2.
  Production configuration and cron frequency were not changed.
- The temporary HTTP entrypoint required a random bearer token. It invoked the
  real queue/scheduled programs with the real Neon, crypto, DNS and HTTP adapters.
  Instrumentation recorded query durations without query parameters. Real queue
  tests used actual Cloudflare queue callbacks, not the HTTP surrogate.
- Two baseline and two final measurement repetitions. Each controlled delivery
  repetition excluded three warm-up batches, then measured 30 batches of 10;
  each measured 20 small dispatches and 20 idle passes. Each load repetition
  measured three 500-event recovery passes and a 1,000-delivery queue burst.
- Worker durations use the Worker's monotonic clock. Client durations include the
  caller-to-Worker round trip. SQL timestamps independently measure event/delivery
  commit to persisted terminal state. CPU comes from Cloudflare's persisted
  `$workers.cpuTimeMs`, not elapsed time or a local CPU estimate.
- Reported wall-time percentiles use the nearest-rank definition. Recovery has
  only six samples per variant; its P95/P99 are observed maxima, not stable tail
  estimates. There are only two queue bursts per variant, so they are listed
  separately rather than presented as a statistically established speedup.

## CPU

The persisted observability queries returned all six loaded recovery invocations
per variant with `sampleInterval = 1`. The workload population was separated from
idle passes by script version, request path and wall-time bounds; the raw query
filters and counts are recorded in `cpu-recovery.json` in the results bundle.

| Loaded recovery CPU, ms | Baseline | Final |
| --- | ---: | ---: |
| P50 | 365 | 8 |
| Mean | 371.5 | 9.33 |
| P95 / P99, six samples | 398 / 398 | 13 / 13 |

The P50 CPU reduction is **97.81%** for this workload. Removing hundreds of SQL
and queue calls also removes their Effect orchestration, decoding and network
adapter work. This does not mean overall production CPU falls by that percentage.
Memory and sustained multi-hour throughput were not measured.

## Actual Cloudflare queue bursts

Each burst seeded and directly queued 1,000 delivery IDs, bypassing initial cron
alignment and event dispatch. All rows finished successfully, with exactly
1,000 persisted attempts, 1,000 unique valid receiver receipts and 1,000 receiver
requests. The table measures commit → persisted completion, including queue wait,
claim, DNS, HTTP and completion SQL, not just the HTTP receiver's response time.

| Run | P50, seconds | P95, seconds | P99, seconds | Last finalized delivery, seconds |
| --- | ---: | ---: | ---: | ---: |
| Baseline 1 | 36.640 | 42.323 | 43.122 | 43.335 |
| Baseline 2 | 27.770 | 35.305 | 36.296 | 36.329 |
| Final 1 | 26.068 | 32.051 | 32.649 | 32.700 |
| Final 2 | 27.887 | 35.120 | 35.757 | 36.316 |

This is a successful delivery/regression check. The direct-delivery code path is
unchanged in the final variant; the run-to-run difference must not be attributed
to the recovery optimization. Actual queue invocations also had much larger
database and receiver round-trip times than the European HTTP surrogate, which
is why controlled batch durations cannot be substituted for queue latency.

Event queue drainage is separate from recovery enqueue time. One experimental
run exceeded the original 60-second drain deadline; its markers later all
cleared. Final drain deadlines were 180 seconds and both final repetitions
completed. Fast enqueue is not a bound on queue scheduling latency. The existing
one-minute cron alignment and durable retry deadlines remain unchanged.

## Retained implementation

1. Stop pagination after a page smaller than 500, rather than issuing a known
   empty read. An exact 500-row page still probes the next page. Boundary tests
   cover 0, 1, 499, 500, 501 and 1,001 deliveries.
2. Submit event IDs in platform-supported batches of at most 100. Await all
   batches before deferring the selected outbox rows in one parameterized UPDATE.
3. Preserve `dispatch_at IS NOT NULL` so a fast consumer's cleared marker is not
   resurrected. Partial queue submission or a failed defer leaves un-cleared
   rows recoverable; duplicate queue messages remain safe.

The independent delivery recovery scan, atomic claims, lease fencing, signature
format, DNS checks, payload snapshots, retry policy and retention logic were not
removed or weakened. No DNS/secret cache or new dependency was introduced.

## Rejected experiment

Per-invocation delivery concurrency 10 reduced controlled batch P50 from about
119 ms to 97 ms, but one real 1,000-delivery burst took 83.125 seconds to finalize
its last delivery. A subsequent event burst exceeded the original drain deadline.
These results do not prove concurrency caused those outliers, but they do not
justify retaining the change. The final implementation restores concurrency 5.
Experimental measurements and the failed run are retained in the results bundle,
not silently mixed into final results or discarded as successful repetitions.

## Feature verification

The ten regression cases added during this benchmark were subsequently removed
on request. The original 64 cases remain; their queue mocks retain the required
adapter for the new batched event service. The 74-test result below records the
verification performed at benchmark time, not the current suite size.

- **74 local tests, 0 failures**, plus package typecheck, scoped lint/format check,
  deployment dry-run and `git diff --check`. Existing assertions were retained.
- On the deployed final Worker: 200/204 success, 400/302 terminal failure,
  408/429/503 retries, numeric Retry-After persistence, ten concurrent duplicates
  plus redelivery producing only one attempt/request, and ten approximately
  60-KB signed payloads.
- Real public DNS resolving to loopback was rejected before HTTP. IP-literal
  destinations and corrupted encrypted secrets failed terminally. A receiver
  delaying 11 seconds produced an exactly 10,000-ms timeout and a persisted retry.
- All twelve event headers and exact raw-body HMACs were checked against the
  independent receiver. Separately, all twelve valid producer payloads were
  written through the real Effect producer and Neon adapter, with repeated source
  keys returning the existing event.
- Real PostgreSQL post/GEO triggers covered create, update, timestamp-only no-op,
  publish, unpublish, republish, delete and terminal GEO completion/failure. An
  intentionally failing transaction (`22012`, division by zero) rolled back the
  post, outbox and fanout together. All 23 resulting producer/lifecycle deliveries
  succeeded and were independently HMAC-verified.
- Regression coverage includes partial event-batch failure, enqueue followed by
  failed bulk defer, a consumer clearing dispatch before defer, tenant isolation,
  cancellation, retention, expired claims, stale completions, manual retry,
  atomic producer writes and all event schemas. These are package/integration
  checks, not an authenticated dashboard/API browser test.

## SimStudio comparison

The inspected [SimStudio processor at `7d0fdefb`](https://github.com/simstudioai/sim/blob/7d0fdefb/apps/sim/lib/webhooks/processor.ts)
routes incoming workflow executions through inline/job/BullMQ paths according to
provider and configuration. That is an incoming webhook workflow execution
system, whereas this package delivers outgoing webhooks. Its async separation is
useful context, but copying an inline ingress path would not replace Notra's
transactional outbox or justify weakening retries. No comparative SimStudio
performance number or live SimStudio integration test is claimed.

## Evidence and cleanup

The results bundle attached to the benchmark conversation contains the
measurement scripts, receiver, baseline and final source snapshots, percentile
summaries, per-request query/HTTP timing
JSON, queue outcomes, CPU aggregates, protocol/producer checks and rejected
experiment notes. It contains no database URLs, bearer tokens or signing keys.
Raw tails containing request headers are deliberately excluded.

The temporary Worker and both queues were deleted. The Railway deployment was
stopped, its receiver service removed, and project deletion requested; Railway
soft-deletes projects on its own schedule. The empty benchmark Neon project was
deleted. The live tail was stopped and local temporary credentials removed.
No existing Worker, production deployment, application database or production
migration was changed by the benchmark deployments.
